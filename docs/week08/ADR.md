# ADR：用受限排程專家延伸現有學生安排 API

狀態：已實作，OpenAI 真實連線待驗證。

## 問題與決定

需要新增多 Agent API 及可查證介面，同時維持原本 React 前端。採 Flask 同源獨立 `/agent-lab`，使用公開 `/api/v1/agent` 契約，避免另建前端依賴與跨來源設定。日後原前端可直接整合 API。

採中央助理 + 一位受限專家（Agent-as-tool），不做 Handoff。學生助理保留最終整合責任；專家上下文獨立，且只能取得空檔及候選。增加角色的可觀察成果是委派、工具白名單、交付來源、共同驗收，而非假設多 Agent 一定較好。

保留既有 deterministic 排程引擎，AI 不負責時間算術及資料庫寫入。`finish` 的時數及來源由程式比對；自然語言說明標記未作完整語意驗證。這降低模型自行捏造時段的可能，但也限制初版不能用自由文字指示更換排程策略。

使用一致性快照避免在模型請求中長時間持有資料庫交易。候選來源保留版本，查證與儲存均對照現在資料；版本不一致須重新產生。這可能拒絕仍可使用但來源已有變化的候選，選擇可解釋的一致性優先。

保存紀錄採新增 agent_runs 表；commit 使用現有 study-plan/session 儲存流程，在同一寫入交易內完成。相同 run 的確認為冪等，不會重複建檔。產生 run 本身非冪等，重送會建立不同執行紀錄；因此 UI 在執行中停用重送。

## 比較方式與已知取捨

離線正常流程 single 為 3 個腳本回合、multi 為 5 個腳本回合，兩者真實模型請求數為 0。相同需求與快照會得到相同候選，這只能證明控制及整合契約，不能證明模型準確度、延遲或成本優勢。

真實比較須保持模型、資料版本、需求及共同終點相同，保存 model_calls、tokens、usage_complete、latency_ms 與查證結果。尚未配置 OpenAI 金鑰，因此未宣稱真實 MAS 效益。

未使用外部 MAS 框架：初版僅兩個角色與少量工具，Python 控制層足以讓控制權、上限與驗收可見。若後續新增背景任務、取消、串流或多專家，需重新評估編排方式。
