## 2:45–3:55 系統架構

講者：張華庭

> 使用者在 React 輸入需求，Vite 將 API 請求轉到 Flask。Flask 先做 schema 與語意驗證，再由後端透過 Application Default Credentials 呼叫 Vertex AI Gemini。模型只能提出 allowlist 內的 function call。Host 會逐欄比對模型參數與原始需求，通過後才執行確定性排程工具。工具結果會以 functionResponse 回到模型，最後才整理成說明。
>
> 待辦、行程、讀書時段、偏好、課表、修課紀錄和規則都保存在同一個 SQLite。瀏覽器不保存 API key，也不持有 ADC token。

## 3:55–4:55 兩個工具介面

講者：張華庭

> 第一個工具是 get_validated_study_plan。輸入包含日期、總時數、單次時長、允許時段、課程和私人行程，輸出 sessions、已安排分鐘與尚缺分鐘。它是唯讀工具，會經過 schema、日期、衝突和時數驗證。
>
> 第二個工具是 save_study_plan。輸入是已驗證 preview、confirmed 和 request_id。沒有確認就不寫入；相同 request_id 與相同內容只回放結果，不會新增第二批資料；相同 ID 但不同內容會被拒絕。

> 目前網站主 Agent 只自動呼叫第一個唯讀工具。第二個寫入工具已完成程式與測試，由 Host 在確認後控制，尚未讓主模型自行選擇。這是我們目前刻意保留的安全界線，也是期末要完成的整合項目。

## 問答準備

### 為什麼需要 Agent，而不是全部寫規則？

規則適合日期、衝突、學分和權限；模型適合理解需求、選擇受限工具與說明結果。兩者分工才能兼顧彈性與可驗證性。

### 為什麼不做完整 RAG？

主排程只需要本輪結構化資料。畢業規則目前是版本化本機來源；等正式接入多份校務文件並需要跨版本檢索後，再引入向量索引或 hybrid retrieval。

### 為什麼不用 MCP？

目前只有單一 Web 應用與少量內部工具，直接 Function Calling 的介面較小且容易驗證。MCP 適合多個 Host 重用外部工具；目前尚未實作，報告不會把 REST API 稱為 MCP。

### 你們怎麼避免模型亂改參數？

後端保存原始 normalized request，再把 function-call arguments 重新 normalize 並逐欄比較。不一致就停止，工具呼叫數維持零。

### 如何避免重複寫入？

寫入工具要求 request ID。相同 ID 和相同 payload 回傳第一次結果；相同 ID 搭配不同內容會被拒絕。偏好記憶另使用 operation ID 與 expected version。

### 為什麼畢業學分是待確認？

整合規格要求通過和認列分開。共同認列範圍目前是 `null`，代表尚未提供，不是空清單；系統因此保留紀錄但不冒充確認學分。

### Gemini 到底有沒有成功？

本報告版本沒有完成真實 Gemini／ADC 呼叫，狀態是 `LIVE_NOT_RUN`。OpenAI 選用後端曾有 `LIVE_PASS`，但不能取代課程指定的 Gemini 證據。
